# Qlik Sense Enterprise on Windows (client-managed): what happens to a departed user's sheets (community, published, approved/base, private)

Scope: client-managed Qlik Sense Enterprise on Windows (QSEoW) administered via the QMC/QRS only. Qlik Cloud is out of scope except where noted as contrast. Research date: 2026-10-16. Most official help pages fetched were the May 2025 (sense-admin) and May 2026 (Hub) editions; older community threads are flagged with dates.

## 1. What happens to app objects (sheets, stories, bookmarks) when the owner is removed from AD/LDAP, marked "Removed externally", blocked/inactivated, or deleted in the QMC?

### Takeaway
There are two distinct states. While a user is only inactive ("Removed externally" after a UDC sync, or "Blocked" by an admin), they keep ownership of all their objects and nothing is deleted. When an admin deletes the user in the QMC, Qlik does not delete their objects. Ownership of everything the user owned moves to the built-in `sa_repository` account, and only the user record and its custom properties are removed. I found no official QSEoW setting that automatically deletes "Removed externally" users. Deletion is documented only as a manual QMC action, a QRS API call, or an option offered when you delete the User Directory Connector itself.

### Cited Findings
- **Deleting a user moves ownership instead of deleting content:** "The ownership of the user's objects is moved to the sa_repository user." "All other information regarding the user, such as custom properties, is deleted along with the user." The deleted user "will not be granted access from the security evaluation." — [Qlik help: Deleting users (QSEoW May 2025)](https://help.qlik.com/en-US/sense-admin/May2025/Subsystems/DeployAdministerQSE/Content/Sense_DeployAdminister/QSEoW/Administer_QSEoW/Managing_QSEoW/delete-users.htm)
- **The same behaviour is documented in older releases** (April 2018 help, Qlik Sense 1.1 help), so it has been stable across versions — [Qlik help: Deleting users (April 2018, de-DE)](https://help.qlik.com/de-DE/sense/April2018/Subsystems/ManagementConsole/Content/Sense_QMC/delete-users.htm); [Qlik Sense 1.1 help: Deleting users](https://help.qlik.com/sense/1.1/en-US/online/Subsystems/ManagementConsole/Content/QMC_Resources_Users_DeletingUsers.htm)
- **Removal from the directory only inactivates the user:** "Users that are deleted from the directory service that Qlik Sense connects to are automatically inactivated in the QMC." — [Qlik help: Deleting users (May 2025)](https://help.qlik.com/en-US/sense-admin/May2025/Subsystems/DeployAdministerQSE/Content/Sense_DeployAdminister/QSEoW/Administer_QSEoW/Managing_QSEoW/delete-users.htm)
- **Inactive users keep their objects.** Admins can block users, who then show as "Blocked". Qlik Sense also inactivates users automatically when they are removed from the connected directory and labels them "Removed externally". Both kinds of inactive user keep ownership of the objects they created or were assigned, and keep their custom properties. An inactive user who tries to log in is told to contact the system administrator. A RootAdmin with "Delete prohibited" cannot be inactivated until that setting is cleared. — [Qlik help: Inactivating users (May 2025)](https://help.qlik.com/en-US/sense-admin/May2025/Subsystems/DeployAdministerQSE/Content/Sense_DeployAdminister/QSEoW/Administer_QSEoW/Managing_QSEoW/inactivate-users.htm)
- **Deleting the UDC can delete its users:** when you delete a user directory connector, you can choose to delete all users imported from that directory — [Qlik help: Deleting users (May 2025)](https://help.qlik.com/en-US/sense-admin/May2025/Subsystems/DeployAdministerQSE/Content/Sense_DeployAdminister/QSEoW/Administer_QSEoW/Managing_QSEoW/delete-users.htm)
- **"Removed externally" defined:** the flag means users "have been removed from the directory that Qlik Sense is connected to" and they are treated as inactivated users. Deleting a user in the QMC does not change the source AD (2018 community test) — [Qlik Community: Deletion of Users in Qlik Sense (June 2018)](https://community.qlik.com/t5/QlikView-Administration/Deletion-of-Users-in-Qlik-Sense/td-p/60058)
- **What the Admin Playbook says about inactive users:** "A user is marked inactive when a configured User Directory Connector (UDC) can no longer find the user" in AD/LDAP. "Such users are candidates for license deallocation if they have left the company." — [Qlik Sense Admin Playbook: License Maintenance](https://help.qlik.com/en-US/qs-admin-playbook/Content/licensing/license_maintenance.htm)
- **Deleting objects through the QMC/QRS:** a Qlik staff member noted that deleting sheets in the QMC goes through the Repository API and "does not remove the actual sheet from the binary on disk as the Qlik Repository Service does not operate on this level." — summarized from [Qlik Community thread on admin deletion of community sheets](https://community.qlik.com/t5/New-to-Qlik-Analytics/How-can-an-administrator-delete-a-community-sheet-published-by-a/m-p/1156612) (search-snippet level; not re-verified on the page)
- **Community and personal sheets live inside the app's .qvf** in the Qlik Sense share storage, not in a per-user store. "Community and Personal sheets are kept in the binary file (.qvf) file stored in the Qlik Sense share storage." — [Qlik Support article: How to backup, migrate or import community and personal sheets to Qlik Sense Enterprise on Windows (updated 2024-02-20)](https://community.qlik.com/t5/Official-Support-Articles/How-to-backup-migrate-or-import-community-and-personal-sheets-to/tac-p/2419491)
- **Contrast with Qlik Cloud:** in Qlik Cloud, deleted users' assets are left with no owner ("Any assets they own will no longer have an owner"). On-prem reassigns them to `sa_repository`. — [Qlik Cloud help: Deleting users](https://help.qlik.com/en-US/cloud-services/Subsystems/Hub/Content/Sense_Hub/Admin/SaaS-delete-users.htm)

### Inferences
- In QSEoW the term "orphaned" is loose. A deleted user's sheets, stories and bookmarks are not ownerless. They are owned by `sa_repository`, which is an internal service account that no human logs in as. In practice they are orphaned: nobody can edit, unpublish or delete them from the hub, and only an admin working in the QMC or QRS can act on them.
- Merely leaving the company (the AD account is disabled or removed, and the UDC sync flags the user "Removed externally") changes nothing about the objects. The user still owns them, with the same publish and approve state, until an admin deletes the user.
- Because sheets physically live inside the app's .qvf, the risks to a departed user's sheets come from operations on the app, not on the user. Deleting the app, or publishing a new app ID in its place, removes all community and private sheets.

### Gaps
- I could not confirm that any QSEoW release (through May 2026) has a UDC or QMC setting such as "Delete removed externally users" that deletes inactive users automatically. The official Inactivating users page describes deletion only as a manual action. A community answer says to delete them manually (filter Removed externally = Yes) or through the QRS API ([Qlik Community: What does Removed externally mean in QMC USERS](https://community.qlik.com/t5/Visualization-and-Usability/What-does-Removed-externally-mean-in-QMC-USERS/td-p/871010)). Treat claims of an automatic purge setting as unverified.
- One search snippet said Qlik Support stated that clearing the "Removed externally" flag was not possible, that the only option was to delete and recreate the user and change object ownership manually, and that a feature request had been logged. I did not open the page to confirm which thread or release this came from (it was possibly [this thread](https://community.qlik.com/t5/Deployment-Management/AD-Users-Connection-filter-quot-Removed-Externally-quot-users/m-p/1646985)).
- A related risk was not documented: if the user is deleted and later comes back into Qlik through a UDC sync or login, Qlik creates a new user record with a new GUID, and old content is not reattached. This is inferred from the GUID-based ownership model and is not documented.

## 2. Can consumers still see the community/published sheets of a removed or deleted user? Do owner-based security rules break?

### Takeaway
Yes, by inference from the default rules, though Qlik does not document this outright. The default "Stream" security rule grants read on published app objects to everyone who can read the app's stream, and it does not test who owns the object. A published (community) or approved (base) sheet therefore stays visible to stream consumers whether its owner is active, inactive, or deleted (with ownership moved to `sa_repository`). What breaks is everything that depends on the owner. Private (unpublished) sheets become reachable by no human user, nobody can unpublish or edit community sheets from the hub, and any custom rule keyed on `resource.owner` stops matching the departed person.

### Cited Findings
- **The default Stream rule covers published App.Objects.** Per Qlik Support, objects inherit rights from the app or stream. The rule covers App.Objects that are published and not of type `app_appscript` or `loadmodel`, when the user can read the stream. It uses `resource.app.stream.HasPrivilege("read")`, and the App part is `resource.resourcetype = "App" and resource.stream.HasPrivilege("read")`. — [Qlik Support article 000046126 (search-summary level)](https://support.qlik.com/articles/000046126); see also [Qlik Support: Hierarchical relationships in Security Rules for Qlik Sense](https://community.qlik.com/t5/Official-Support-Articles/Hierarchical-relationships-in-Security-Rules-for-Qlik-Sense/ta-p/1711781/highlight/true)
- **Preinstalled rules list (April 2018)** includes CreateAppObjectsPublishedApp, which uses `resource.App.stream.Empty()` and `resource.App.HasPrivilege("read")` — [Qlik help: Security rules installed in Qlik Sense (April 2018, de-DE)](https://help.qlik.com/de-DE/sense/April2018/Subsystems/ManagementConsole/Content/Sense_QMC/preinstalled-QMC-security-rules.htm)
- **Owner-based access ends when the user is deleted:** a deleted user "will not be granted access from the security evaluation" — [Qlik help: Deleting users](https://help.qlik.com/en-US/sense-admin/May2025/Subsystems/DeployAdministerQSE/Content/Sense_DeployAdminister/QSEoW/Administer_QSEoW/Managing_QSEoW/delete-users.htm)
- **Inactive users cannot log in at all**, so owner rules no longer serve them, but ownership is unchanged — [Qlik help: Inactivating users](https://help.qlik.com/en-US/sense-admin/May2025/Subsystems/DeployAdministerQSE/Content/Sense_DeployAdminister/QSEoW/Administer_QSEoW/Managing_QSEoW/inactivate-users.htm)
- **Community view on who can remove community sheets.** One community reply says "The community sheets are deletable only by its owner (unpublish - then delete)". Another says an admin can do it from `https://{server}/qmc/appobjects`, filtering by app and owner, where the sheet shows Published = yes and Approved = no. — [Qlik Community thread (m-p/1156612)](https://community.qlik.com/t5/New-to-Qlik-Analytics/How-can-an-administrator-delete-a-community-sheet-published-by-a/m-p/1156612); [same thread (m-p/1156610)](https://community.qlik.com/t5/New-to-Qlik-Analytics/How-can-an-administrator-delete-a-community-sheet-published-by-a/m-p/1156610)
- **Qlik's Admin Playbook** says community sheets should normally be removed manually and the responsibility left to app owners. It describes scripted bulk removal through Qlik-Cli only for large cleanups and says base sheets should never be removed programmatically. — [Qlik Sense Admin Playbook: Flag Unused Base/Community Sheets](https://qsadminplaybook.qps.qlik.com/docs/asset_management/apps/flag_unused_base_community_sheets.html)
- **Customizing the default Stream rule is risky:** users report sheets disappearing after replacing the default Stream rule with a custom app-level rule, and default bookmarks failing to load after disabling it — [Qlik Community: App level access but issue in app object access](https://community.qlik.com/t5/Deployment-Management/App-level-Access-in-Qliksense-but-issue-in-app-object-access/m-p/1528558/highlight/true); [Qlik Community: Security rule for bookmark loading](https://community.qlik.com/t5/New-to-Qlik-Analytics/Security-rule-for-Bookmark-loading/td-p/1654820)

### Inferences
- With default rules, consumers keep seeing a departed user's community sheets and approved base sheets, both before and after the user is deleted, because the Stream rule tests `published` and stream read rights, not the owner.
- Custom rules that reference `resource.owner.*` (for example `resource.owner.userDirectory`, `resource.owner.@Department`, or `resource.owner = user`) can change behaviour after deletion. The owner becomes `sa_repository`, which has no custom properties and typically uses the INTERNAL directory, so such rules may stop granting, or start denying, access to those objects. Admins should review custom rules for `owner` references before bulk-deleting users.
- Community sheets owned by `sa_repository` effectively become frozen content. Consumers can view them, but nobody can maintain them through the hub. An admin must reassign ownership (section 3) or approve the sheet (section 6).

### Gaps
- I did not find an official Qlik page or support article that states plainly: "community sheets of a deleted user remain visible to stream consumers." This conclusion rests on the default Stream rule's logic plus the documented ownership transfer. It should be validated in a test environment for the specific release.
- I could not retrieve the exact current (2025/2026) default rule text from help.qlik.com. The May 2025 "default security rules" URL I tried returned 404. Conditions are quoted from the Qlik Support article summary and the April 2018 help.
- Whether a RootAdmin can see another user's private sheets in the hub (as opposed to in the QMC App objects list) was not confirmed by any source.

## 3. How do admins change the owner of app objects/sheets (QMC, QRS API, Qlik-Cli-Windows, bulk)?

### Takeaway
In the QMC, open App objects, filter by owner and/or app, select one or many objects, choose Edit, change Owner in the Identification section, and Apply. Multi-select lets you reassign all of one departed user's objects in a single edit. Programmatically, GET `/qrs/app/object/{id}`, replace `owner.id` with the new user's GUID, and PUT it back to `/qrs/app/object/{id}`. Qlik-Cli-Windows wraps this as `Update-QlikObject -id <id> -owner <user>`, which also has an `-approved` switch. I found no dedicated Qlik "orphaned objects" utility for QSEoW.

### Cited Findings
- **QMC editing:** "You can edit app objects that you have update rights to." To edit, select App objects, select the objects, click Edit, change properties, and click Apply. The editable Identification properties are Name (required) and Owner. — [Qlik help: Editing app objects (QSEoW May 2025)](https://help.qlik.com/en-US/sense-admin/May2025/Subsystems/DeployAdministerQSE/Content/Sense_DeployAdminister/QSEoW/Administer_QSEoW/Managing_QSEoW/edit-app-objects.htm)
- **Rules for changing ownership:** the creator is the default owner, an admin with sufficient rights can reassign ownership by editing the resource, and the new owner must already exist in the system — [Qlik help: Changing ownership of resources (April 2018, es-ES)](https://help.qlik.com/es-ES/sense/April2018/Subsystems/ManagementConsole/Content/Sense_QMC/change-ownership-of-resources.htm)
- **Bulk in the QMC:** a customer migrating domains (2020–2021) found no scripted method and "had to do it manually for several thousand of objects". The workaround was to filter the App objects list by one owner, multi-select all of that user's objects, and change the owner in one edit. — [Qlik Community: Batch change ownership of app objects](https://community.qlik.com/t5/New-to-Qlik-Analytics/Batch-change-ownership-of-app-objects-in-Qlik-Sense/m-p/1800764)
- **QRS API single object (accepted answer by Levi_Turner):** `GET /qrs/app/object/{id}`, set `owner.id` to the new user's GUID (optionally also `userId`, `userDirectory`, `name`), then `PUT /qrs/app/object/{id}` with the modified JSON. Minimal owner block: `"owner": {"id": "<new-user-guid>"}`. A follow-up poster noted that renaming a sheet this way updated the QMC but not the hub. — [Qlik Community: Change ownership of Qlik Sense object using QRS API](https://community.qlik.com/t5/Integration-Extension-APIs/Change-ownership-of-Qlik-Sense-object-using-QRS-API/m-p/1780770)
- **QRS API bulk through a selection and synthetic PUT (2016 thread).** First POST a selection, e.g. `{"items":[{"type":"App","objectID":"<app-id>"}]}`. Then PUT to the synthetic endpoint with a `properties` array (`name: "owner"`, `value: <user id>`, `valueIsModified: true`) plus `type` and `latestModifiedDate`. The poster reported `qrs/Selection/{0}/App/Object/synthetic` as the working URI. Other users got errors with variants, and one hit errors from a missing xrfkey. — [Qlik Community: How to change App/AppObject owner using the API](https://community.qlik.com/t5/Integration-Extension-APIs/How-to-change-App-AppObject-owner-using-the-API/td-p/1182928)
- **Qlik-Cli-Windows (`ahaydon/Qlik-Cli-Windows`, community-maintained PowerShell module).** `Update-QlikObject` takes `-id`, `-name`, `-owner` and `-approved`. It GETs the object, sets `$obj.owner = GetUser $owner` and/or `$obj.approved`, and PUTs to `/qrs/app/object/$id`. `Get-QlikObject -filter` queries `/qrs/app/object`. `Publish-QlikObject` and `Unpublish-QlikObject` call `/qrs/app/object/$id/publish` and `/unpublish`. `Remove-QlikObject` DELETEs `/qrs/app/object/$id`. `Update-QlikApp -owner` changes app ownership. — [GitHub: Qlik-Cli-Windows resources/object.ps1](https://github.com/ahaydon/Qlik-Cli-Windows/blob/master/resources/object.ps1); [resources/app.ps1](https://github.com/ahaydon/Qlik-Cli-Windows/blob/master/resources/app.ps1)
- **Bulk-script pattern (inferred from the cmdlet source; not an official script):** `Get-QlikObject -filter "owner.userId eq 'jdoe' and owner.userDirectory eq 'CORP'" | ForEach-Object { Update-QlikObject -id $_.id -owner 'CORP\newowner' }`. After deletion, filter on `owner.userId eq 'sa_repository'` instead. Note that `sa_repository` may also legitimately own other objects.
- **The modern `qlik` CLI (Go-based) `qlik app object change-owner --appId --objectId --ownerId` targets Qlik Cloud.** Qlik's migration doc notes that the object ID is `engineObjectId` on client-managed and `objectId` in Cloud. It also states: "Any object that is not part of the base (approved) part of an app can have an owner different from the parent app." — [qlik.dev: Migrate app objects with qlik-cli](https://qlik.dev/manage/migrate/qlik-cli-app-objects-migrate/); [qlik.dev changelog: qlik-cli update](https://qlik.dev/changelog/42-qlik-cli-update/)

### Inferences
- The most practical offboarding runbook for QSEoW is:
  1. Before deleting the user, while their objects are still attributable to them, filter QMC App objects by Owner = departing user.
  2. Bulk-edit Owner to a successor or a service "content steward" account.
  3. Deallocate the license.
  4. Delete the user.

  After deletion, everything is lumped under `sa_repository`, and you can no longer tell whose objects were whose from the owner field alone.
- The QRS approach is per-object and needs a certificate or a header-authenticated virtual proxy with an admin user. Qlik-Cli-Windows (`Connect-Qlik`) handles this, but it is a community module rather than a Qlik-supported product.

### Gaps
- I found no official Qlik support (knowledge-base) article for QSEoW titled along the lines of "orphaned sheets after user deleted". The community threads above are the main sources.
- I did not verify the exact current QRS API reference page for `PUT /qrs/app/object/{id}` on help.qlik.com/qlik.dev for 2025/2026. The endpoint behaviour is documented through community answers and the Qlik-Cli source.
- Whether changing the owner in the QMC takes effect immediately for open hub sessions on QSEoW was not documented. The qlik.dev Cloud doc mentions eventual consistency for ownership changes.

## 4. Can private (unpublished) sheets of a departed user be recovered by an admin by changing owner?

### Takeaway
Probably yes on QSEoW, as long as the app still exists. Private sheets are QRS app objects inside the app's .qvf and are listed in QMC App objects (Published = No). Reassigning the Owner to another user should make them appear under that user's "My sheets". This is reported by community users rather than stated in official docs. The documented alternative is to copy the app's binary from the share and import it, which turns every sheet into a base sheet owned by the importing admin. On Qlik Cloud, by contrast, admins cannot recover another user's private sheets, so recovery reports from Cloud do not apply to QSEoW.

### Cited Findings
- **QMC owner change works for sheets and stories:** a community user found that in QMC "App Objects" you can change the owner from the original owner to someone else for objects of type sheet or story, though there is no copy option. The thread also suggests having the owner publish a private sheet as a community sheet so it can then be approved as a base sheet. — [Qlik Community: How to access another user's duplicated sheets](https://community.qlik.com/t5/New-to-Qlik-Analytics/How-to-access-another-user-s-duplicated-sheets-that-have-been/m-p/1808889); [same thread](https://community.qlik.com/t5/Visualization-and-Usability/How-to-access-another-user-s-duplicated-sheets-that-have-been/m-p/1808838)
- **Private sheets follow ownership changes:** in a 2021 QSEoW case, after an app owner change in the QMC, "all private (unpublished) sheets moved from user B to A". This shows that private sheets are tied to the QRS owner and reassignable, though here as an unwanted side effect. — [Qlik Community: Losing private sheets (2021-03-16)](https://community.qlik.com/t5/Management-Governance/Losing-private-sheets/td-p/1791845)
- **The binary-copy recovery route (official support article for QSEoW):**
  1. Find the app ID in QMC > Apps.
  2. Locate the file in the app folder shown under QMC > Service cluster.
  3. Copy the file and add the `.qvf` extension.
  4. Import it in QMC > Apps > Import. All sheets then appear as base sheets.

  "All objects in the app (including bookmarks, snapshots, and so on) will be assigned to the App owner (admin importing the app), and all prior ownership information and publish states will be lost." The default QMC Export does not include personal or community sheets. One commenter reported that only about 400 of 1,100+ personal sheets came through. — [Qlik Support: How to backup, migrate or import community and personal sheets (QSEoW)](https://community.qlik.com/t5/Official-Support-Articles/How-to-backup-migrate-or-import-community-and-personal-sheets-to/tac-p/2419491); related [support.qlik.com article 000077992](https://support.qlik.com/articles/000077992)
- **Deleting and republishing the app wipes these sheets:** deleting and re-publishing an app changes its app ID, and the community sheets are wiped — [Qlik Community thread (search-snippet level)](https://community.qlik.com/t5/New-to-Qlik-Analytics/How-can-an-administrator-delete-a-community-sheet-published-by-a/m-p/1156612)
- **Snapshot restore:** a community user reported recovering unpublished user sheets through an apps-folder restore, with Repository Snapshot Manager mentioned — [Qlik Community: Recover User Sheets](https://community.qlik.com/t5/New-to-Qlik-Analytics/Recover-User-Sheets/m-p/1157223) (search-snippet level)
- **Contrast with Qlik Cloud, where recovery is not possible:** "scripts, cli, api, automations etc can ONLY change the owner of a sheet when that action is done by the current owner"; an idea is open for tenant admins to change owners of private sheets — [Qlik Community: Recover private sheets that belong to a deleted user (Cloud)](https://community.qlik.com/t5/Move-to-Qlik-Cloud-Analytics/Anyone-ever-found-a-way-to-recover-private-sheets-that-belong-to/m-p/2496045); [Qlik Community: Access private sheets from other users as admin (SaaS)](https://community.qlik.com/t5/Deployment-Management/Qlik-SaaS-Access-private-sheets-from-other-users-as-Adminitrator/m-p/1896540/highlight/true)

### Inferences
- On QSEoW, deleting the departed user does not destroy their private sheets. They move to `sa_repository` and stay in the .qvf, so an admin can still reassign them afterwards through the QMC (filter Owner = sa_repository, App = X, Published = No). Doing it before deletion is cleaner, because afterwards the original author can only be identified by name or created-date heuristics.
- Recovery fails if the app was deleted, or replaced in a way that changes its app ID, before reassignment. It can also fail if a binary import drops some personal sheets, as the support-article comment reports.

### Gaps
- No official Qlik help page explicitly confirms that reassigning a private sheet's owner in the QMC makes it appear in the new owner's "My sheets" in the hub. This rests on community reports.
- I found no documentation on what happens to private bookmarks of a deleted user beyond the generic transfer to `sa_repository`.

## 5. License implications: does the departed user still hold an allocation? The 7-day quarantine; does content survive license removal?

### Takeaway
Licenses are not released automatically when a user is removed from AD or flagged inactive. Professional and Analyzer allocations stay assigned until an admin deallocates them in QMC > License management, or a license rule stops matching. Deallocating professional access puts it into a 7-day quarantine if the user logged in during the last 7 days, otherwise it is released immediately. A quarantined allocation can be reinstated to the same user within 7 days. Deallocating a license does not delete the user or their content. Content is governed by user deletion (section 1), not by licensing.

### Cited Findings
- **Deallocating and quarantine:** "If the access type has been used within the last seven days, the access type is put in quarantine." "If it has not been used within the last seven days, the professional access is removed and the license is released immediately." "You can reinstate quarantined professional access, to the same user, within seven days." — [Qlik help: Managing professional access (April 2019)](https://help.qlik.com/en-US/sense/april2019/Subsystems/ManagementConsole/Content/Sense_QMC/manage-professional-access.htm)
- **Older token-model help (user access passes)** also documents quarantine: a quarantined user cannot access streams and apps in the hub, and the token is unavailable for new allocation until the 7-day quarantine ends — [Qlik help: Managing user access (April 2019)](https://help.qlik.com/en-US/sense/april2019/Subsystems/ManagementConsole/Content/Sense_QMC/manage-user-access.htm); [April 2018 (de-DE)](https://help.qlik.com/de-DE/sense/April2018/Subsystems/ManagementConsole/Content/Sense_QMC/manage-user-access.htm)
- **Inactive users keep their licenses until manually deallocated.** The Playbook says to filter QMC Users by Inactive = Yes, deallocate each user in both the Professional and Analyzer access allocation lists, and check whether an auto-allocating license rule needs updating. — [Qlik Sense Admin Playbook: License Maintenance](https://help.qlik.com/en-US/qs-admin-playbook/Content/licensing/license_maintenance.htm)
- **Community confirmation:** users removed from the directory still held professional licenses until manually deallocated, and a Qlik employee shared a PowerShell approach to deallocating licenses of "Removed externally" users (noting it does not handle the token model) — [Qlik Community: Deallocation of Qlik Sense License](https://community.qlik.com/t5/Deployment-Management/Deallocation-of-Qlik-Sense-License/m-p/1620314/highlight/true)
- **One community reply** says the quarantine depends on the activation method and that there is no quarantine with the Professional License/SLK method. This conflicts with the general help wording and is unverified. — summarized from search results around [Qlik Community: License de-allocation](https://community.qlik.com/t5/Visualization-and-Usability/License-De-Allocation-User-running-Qlik-services/m-p/2117081/highlight/true)

### Inferences
- Deallocating a license only stops the user from accessing the hub. It does not touch their sheets or change ownership, because the licensing help pages say nothing about content and ownership changes only on user deletion. A departed user's community sheets stay visible to others whether or not the user still holds an allocation.
- Offboarding order: reassign content, then deallocate (accepting quarantine if they logged in within 7 days), then delete the user. Deleting a user who still has an allocation is a separate matter. The help pages fetched do not say whether deletion auto-releases the allocation.

### Gaps
- I did not find an official statement on whether deleting a user in the QMC automatically frees their Professional or Analyzer allocation, or whether quarantine applies in that case.
- The quarantine text is from the April 2019 help. I did not confirm wording for the 2024–2026 releases (the mechanism is believed unchanged, but this is unverified).

## 6. Is approving a community sheet (making it a base sheet), or duplicating it, a mitigation?

### Takeaway
Yes, approving is the strongest mitigation. When a community sheet is approved, it becomes a base sheet that belongs to the app rather than the user. Qlik's help implies this by saying that unapproving a sheet makes its original owner the owner again, and qlik.dev says only non-base objects can have an owner different from the app. Base sheets are carried into duplicates and exports and do not depend on the departed user. Duplicating a sheet from the hub creates a private copy owned by the person who duplicates it. Qlik-Cli-Windows can set `approved` via QRS.

### Cited Findings
- **Unapproving restores the original owner:** "If the sheet belonged to another user, they will become the owner again." The sheet moves to "Published by me" or "Community". "A sheet removed from the public sheets is not included if the application is duplicated or exported." — [Qlik Sense on Windows help (May 2026): Removing sheets from the public sheets of an application](https://help.qlik.com/en-US/sense/May2026/Subsystems/Hub/Content/Sense_Hub/Publishing/unapproving-sheets.htm)
- **Base objects follow the app owner:** "Any object that is not part of the base (approved) part of an app can have an owner different from the parent app." — [qlik.dev: qlik-cli app objects migrate](https://qlik.dev/manage/migrate/qlik-cli-app-objects-migrate/)
- **Approving from the hub:** since Qlik Sense June 2018, app owners can approve community sheets (and unpublish them) directly from the hub, without the QMC Utilities "Sheet Approver" add-on. Before that, the Sheet Approver let owners promote community sheets to base sheets. — [Qlik Community: Qlik sense how to approve app objects](https://community.qlik.com/t5/Qlik-Sense-Deployment-Management/Qlik-sense-how-to-approve-app-objects/m-p/1187375/highlight/true); [Qlik Community blog: Qlik Sense QMC Utilities](https://community.qlik.com/t5/Design/Qlik-Sense-QMC-Utilities/ba-p/1464003)
- **Programmatic approval:** Qlik-Cli-Windows `Update-QlikObject -id <id> -approved $true` sets `approved` on the QRS object and PUTs it to `/qrs/app/object/{id}` — [GitHub: Qlik-Cli-Windows object.ps1](https://github.com/ahaydon/Qlik-Cli-Windows/blob/master/resources/object.ps1)
- **The official Hub topic "Adding sheets to the public sheets of an application"** is listed as the companion page (previous topic) to the unapprove page — [Qlik help May 2026 (unapprove page, related topics)](https://help.qlik.com/en-US/sense/May2026/Subsystems/Hub/Content/Sense_Hub/Publishing/unapproving-sheets.htm)
- **Private sheets must first be published as community sheets** before they can be approved as base sheets — [Qlik Community: How to access another user's duplicated sheets](https://community.qlik.com/t5/New-to-Qlik-Analytics/How-to-access-another-user-s-duplicated-sheets-that-have-been/m-p/1808889)
- **The binary-import route** turns all sheets, including personal and community, into base sheets owned by the importing admin — [Qlik Support: backup/migrate community and personal sheets](https://community.qlik.com/t5/Official-Support-Articles/How-to-backup-migrate-or-import-community-and-personal-sheets-to/tac-p/2419491)

### Inferences
- For a departed author's valuable community sheets, the app owner can approve them in the hub (Community section > right-click > Approve). The sheets become base sheets of the app, independent of the departed user, preserved on duplicate and export, and safe from later cleanup of the user's objects.
- Duplicating a community sheet in the hub (consumers can duplicate a published sheet into "My sheets") gives the duplicating user a private copy they own. It preserves content, but other consumers do not see it until it is re-published, and it creates a new object ID. This is general Qlik hub behaviour and was not specifically verified in this research.
- A departed user's private sheets cannot be approved directly (approval applies to published sheets). The admin must first reassign the owner (section 3/4), and the new owner then publishes and the app owner approves. Alternatively, Qlik-Cli `Update-QlikObject -approved $true` may set the flag through QRS. Whether QRS honours `approved=true` on an unpublished sheet was not verified.

### Gaps
- The help page for approving sheets ("Adding sheets to the public sheets of an application") returned 404 at the URL I tried, so the exact help wording on ownership transfer at approval time is inferred from the unapprove page rather than quoted.
- No official source spells out who owns an approved sheet in QRS (app owner vs original author with an approved flag). The unapprove wording ("they will become the owner again") implies the app owner holds it while it is approved.
